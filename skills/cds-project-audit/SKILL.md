# 舊專案盤點（claude-dev-system；自動觸發，只問一次）

**觸發（可判定）**：資料夾算專案（`project-scan.py . --summary` 印「算專案」）、沒有 `.claude/project-scan.json`、而且原始碼檔 ≥10。有專案 CLAUDE.md 也要做（CLAUDE.md 不等於盤點過）。索引存在就跳過，改用 `--check` 看哪些檔變了。

1. **掃描**：`py -3 ~/.claude/claude-dev-system/tools/project-scan.py .`。大專案（原始碼 >300 檔）分批讀：先讀入口與被引用最多的 10 個模組，其餘照盤點清單按需讀，不整個專案一次讀完。
2. **架構與資料流**（寫進 `docs/ARCHITECTURE.md`，以掃描出的真實依賴為準，不憑檔名猜）：入口與執行流程、各模組職責與邊界、模組間呼叫、資料從哪來到哪去、外部服務、設定怎麼被讀、錯誤怎麼傳、耦合過高處、循環依賴、散落多處的功能、重複或矛盾的規則、全域狀態。
3. **問題清單**（寫進 `docs/PROJECT-ISSUES.md`，每條九欄：位置、證據、原因、影響功能、嚴重度與優先級、修法、預期改善、驗證方式、回復方式）。分級：影響正確性／資料／安全的最高，再來模組整合與維護成本，命名風格最低。無法確認用途的檔列「待確認」，不可寫「可刪」。
4. **只問一次**（可判定）：循環依賴 ≥1 組、或單檔 >800 行 ≥3 個、或最高嚴重度問題 ≥1 條 → 對使用者說「盤點完成，N 項問題（M 項高），要不要分階段重整？會花約 X 場對話」。使用者說要 → `cds-modularize`；說不要或不回 → 把 `refactorDecision` 寫成 `declined`＋日期，之後不再問，問題清單留著。門檻都沒到 → 不問，只說一句「已盤點，沒有達門檻的問題」。
5. **閘門照裝**：不管要不要重整，都把 `--check` 與目前循環數當閘門裝進測試（同 `cds-project-init` 第 3 步；工具不在就 skip 不 fail），不讓它再惡化。
5a. **沒有交接紀錄檔就建 PROGRESS.md**：第一節寫盤點結果（問題幾項、幾項高）、重整決定與日期、下一步；有紀錄檔就在最後一節補這幾行。盤點本身改了 ≥3 個檔，照 `cds-session-pickup` 的條件本來就該建。
6. **索引維護**：之後開工 `cds-session-pickup` 先跑 `--check`，改過的檔超過 20 個或動到被引用最多的模組 → 重跑掃描更新盤點；否則沿用。

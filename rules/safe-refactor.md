# 安全重構流程（細則）

1. **建立基準**：記錄改前的測試、型別檢查、建置結果與關鍵輸出（快照）；`tools/depgraph.py <root> --json before.json` 存依賴圖。
2. **保護措施先行**：對要動的模組建「固定輸入→固定輸出」比對（快照測試、輸出逐值比對腳本）。
3. **小步、可回復**：每批一個獨立 commit，可單獨 revert；每批只做一種變更（抽常數、拆檔、解循環）。
4. **行為不變的證明**：純重構改前後輸出逐值／逐字元相同；有意改變的行為另開 commit 並寫進「有意改變的行為」清單。
5. **結構原則**：資料與邏輯分離（大型清單獨立成檔）；長文字具名成常數；隱藏前置條件集中到唯一入口並寫在簽名／文件；同樣樣板 3 處以上才抽共用；表面相似但刻意不同的寫清楚為何不合併。
6. **閘門**：`tools/depgraph.py <root> --max-cycle-files <基準>` 循環不可增加；分層規則用 `--forbid`。
7. **刪除前**確認沒有任何呼叫端（含腳本、排程、測試、文件指名），刪後全套檢查必過。

# 完整規則原文（自 Stock-web 全域工作流規則去專案化，使用者原話、數字、日期原樣保留）

## 規則十一：程式碼結構隨時自主優化，不要等大掃除

起因：2026-09-22 大規模重構（`findInUniverse()` 隱藏 warm-up 前置條件咬了三個呼叫端；某檔 33 條提示詞塞在一個陣列，編輯常因全形／半形標點對不起來失敗）。新增／修改功能時主動套用：
1. **資料與邏輯分離**：大型陣列、清單、對照表獨立成檔，邏輯檔只 import（專案內的實例見專案文件）。
2. **長文字／多規則要具名化**：拆成 `export const RULE_XXX = "..."`，用常數名 grep 定位（專案內的實例見專案文件）。
3. **隱藏前置條件要結構性解決**：集中到唯一入口或具名輔助函式（例：`ensureXxxWarm()` 這類唯一入口），並在被依賴函式的簽名／JSDoc 寫明前提，不能只靠呼叫端註解（同一個坑已咬過三次）。
4. **重複邏輯視情況合併**：完全相同的（字串常數、簡單判斷）合併；表面相似但有正當理由不同的（例如修過排版 bug 的不同定位方式、刻意不同詳細程度的組字函式）保留並寫清楚「為什麼不合併」，合併前先確認差異是懶得對齊還是刻意設計。
5. **同樣樣板出現 3 處以上才抽共用 function／hook**；1、2 處維持現狀，不預先抽象。
6. **檔案職責混雜時，新增功能前先考慮拆分**（例如「組名單＋打分數＋轉文字＋提示詞」全在一檔）。
7. **純重構要驗證輸出不變**：除了 tsc／eslint／build，還要寫小腳本比對改動前後在所有輸入組合下逐字元／逐值相同，不能只憑肉眼。
8. **本規則持續更新**：抓到新一類「會被忘記、會被誤用」的壞味道就補進來。

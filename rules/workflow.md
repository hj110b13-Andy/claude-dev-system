# 通用工作流程（細則）

## 每次任務的生命週期（規格 11.1～11.4）
1. **開始**：先讀專案規則、相關模組、主要介面、測試命令、既有工作狀態（交接紀錄）；全新專案才做初始盤點（`tools/depgraph.py`、`tools/moduleInventory.py`）。
2. **修改前**：寫下目標與驗收條件、受影響模組、相依與資料流、要保留的既有行為、要跑的測試與文件、風險與回復方式。
3. **新增功能**：先用既有擴充點；改核心要說明原因與影響範圍。
4. **完成時**檢查：功能完成？測試通過？影響其他模組？文件要更新？留下待辦？重要決策要記錄？出現新的架構問題？小修不做全專案深度分析，重大架構變更或週期維護才做。

## 排工作流（先排再做）
- 盤點：新需求、上次中斷點、未提交檔、進行中 agent、剩餘待辦。中斷的 agent 優先 SendMessage 接續。
- 依「會動到的檔案」分批，不依需求先後；同檔批次排先後，不同檔批次平行。
- 驗證合併做：同類改動整批改完才驗證一次。
- 先做便宜、能解鎖別人的事；需要使用者決定的一次問完。
- 新需求是累加不是取代：追蹤所有未完成項目直到做完。

## 獨立驗證與卡關升級
- 大改動（新功能、跨多檔、AI 行為、資料正確性）改完派 1 個驗證 agent，限時（建議 30 分鐘、單步 >3 分鐘放棄並記「未能驗證」），只驗這次改動的範圍，通過一句話、問題寫重現步驟／預期／實際。
- 同一類問題連續失敗 2 次：第 3 次同步派 2 個不同模型的 agent 查解法，與自己的嘗試交疊進行。

## 用量收尾（配合 hooks/usage_guard.py）
- 門檻（預設 5 小時 ≥80% 或 7 天 ≥97%，數值在 `dispatch-config.json` 的 `usageThresholdPct`，專案 `.claude/dispatch-config.json` 優先於全域；0.7.0 起直接是兩個數字、沒有方案概念，沒到門檻不提示也不動作）觸發時：不再派新 agent、不開新待辦；能在上限前做完的讓它做完，做不完的通知 agent 收尾（commit、存 patch、交報告）；更新交接紀錄；推送。
- 7 天門檻觸發要寫「詳細版」交接：每個待辦寫到不看對話也能做（背景、原話、根因、檔案、下一步指令、驗收標準）。
- 開始大任務前先 `python ~/.claude/claude-dev-system/hooks/usage_guard.py --print` 估夠不夠，不夠先告訴使用者選項。

## 背景等待
- 等背景工作時定期主動回報（帶實際進度數字），不整段沉默；agent 交完最終報告就停掉它。

# 完整規則原文（自 Stock-web 全域工作流規則去專案化；使用者原話、數字、日期原樣保留）
以下章節編號沿用原規則編號（內文互相引用「規則二第 8 點」等）。專案專屬的數字與步驟留在各專案的 CLAUDE.md／skills／`.claude/dispatch-config.json`。

## 規則二：動手前先排「順又省 token」的工作流（2026-10-10 使用者要求，每次都要做）

1. **盤點**：新回報＋上次中斷做到哪（交接紀錄「接手狀態」、`git status` 未提交檔、被中斷 agent 的 patch）＋進行中的 agent＋剩餘待辦。中斷的 agent 優先用 SendMessage 接續（保留它已查的根因），不要重派從頭查。
2. **依「會動到的檔案／模組」分批**，不是依回報先後：同一組檔案的項目交給同一個執行者一次做完（例：同一功能的流程檔一批；前端小修一批；跨模組的效能／快取單獨一批；研究／回測一批）。會改到同一檔案的批次排先後，不同檔案的批次平行（最多 1～2 個 agent）。
3. **驗證合併做**：AI 行為改動整批改完才跑一次跨模型評測；前端小修整批一次部署、一次線上環境檢查；全部批次上線後只派一個驗證 agent 一次驗完。
4. **先做便宜、能解鎖別人的事**：備份未提交改動、型別／測試確認半成品可用、讀已有的檢查結果；再派 agent；agent 跑的同時我做不衝突的小修。
5. **需要使用者決定的事一次問完**（大工程、改變既有行為、取捨），其他照建議預設直接做。
6. 排好的順序寫進 交接紀錄「接手狀態」，中斷時下次照著接。

8. **重排、精簡、搬移紀錄時不可遺漏細節（2026-10-11 教訓：把待辦改成短格式時精簡掉冷快取實測數字、warm-cache 筆數檢查、CPU 用量檢查三處驗收細節，事後比對才發現）**：改寫「接手狀態」、待辦清單、搬 archive 或精簡任何紀錄時，①使用者原話、根因與證據、數字、驗收標準、日期一律保留，只能移位置不能刪；②改完用程式逐句比對改前改後（把舊段落依標點切句，列出新版找不到的句子），逐條確認是「改寫」還是「真的遺漏」，遺漏的補回後才 commit；③比對結果與補回的項目寫進 commit 訊息。

## 規則三：新需求是「累加」不是「取代」，能並行就並行

使用者中途提到新需求，是加進待辦，不是換題目——追蹤所有還沒完成的項目（含我自己判斷該加的優化）全部做完才能回報完成。只有實際衝突（同一檔案／同一份未提交變更）才排隊並說明原因。每次判斷「還有哪些沒做完」都要重新檢視最近對話與 交接紀錄檔，不憑印象。

## 規則六：獨立驗證循環（範圍＝這次改動的地方，不是全站）

驗證的價值在「獨立」（寫程式的人自己測容易用同一套假設；2026-10-04 就是獨立驗證才抓到「EPS 以為修好、其實快取沒失效」）與「省主對話 token」，不在驗證者模型強弱。
1. **大改動**（新功能、跨多檔、AI 行為／提示詞、資料正確性）：改完派 1 個**獨立驗證 agent**（預設 Sonnet；額度不夠臨時換模型），實際打開線上（或本機執行）環境、用 Playwright 只操作這次改動的功能，像真實使用者驗證畫面。**要求精簡回報**：通過一句話帶過，只有問題才寫重現步驟／預期／實際。
2. **小修正**（一兩處、範圍明確：常數、措辭、快取鍵）：我自己用 curl／腳本／tsc 驗證，驗證方式寫進回報與 交接紀錄。
3. agent 回報問題後我先自己修；修不好就讓驗證 agent（或另派 agent）直接改（不套用規則七）；我自己修卡關時套用規則七。
4. 修正後針對該問題複查（大的派同一個驗證 agent、小的自己驗），確認修好才能回覆「更新完成」。全站地毯式檢查只在使用者明確要求時才做。

## 規則七：問題卡關升級

- 同一類問題連續失敗 2 次：第 3 次嘗試時同步派 2 個不同模型的 agent（用 `model` 參數，例如 Opus＋Haiku 或 Sonnet＋Opus）上網查解法，與我的嘗試同時進行。第 3 次仍失敗：依查到的解法繼續試，agent 繼續找新解法，「我嘗試」與「agent 查詢」交疊進行直到解決。失敗次數只對同一類問題累計，換問題歸零。

## 規則八：背景等待時主動回報（每 5 分鐘，附實際進度數字）

- 等待背景工作（指令、部署、agent）時，用 **Monitor 工具**開心跳監看（例如 `while true; do sleep 300; echo "還在等XXX，已過N分鐘，進度…"; done`），每行輸出觸發我主動回報，不能整段沉默、也不能只靠「完成才通知」。**2026-10-06 使用者要求每 5 分鐘**（之前 10-04 曾改成 10 分鐘以減少多 agent 時的訊息量）；心跳要帶實際進度數字（例如評測題數、最新 commit、未提交檔數），沒新進展一兩句帶過。Monitor 單次最長 30 分鐘，到期要重開。使用者問進度要立刻誠實回報；agent 顯示完成卻沒收到報告，主動 SendMessage 去問。
- **教訓**：這條曾被誤改成「技術上做不到、只能等有人問」——沒查證就寫的錯誤結論。**修改 CLAUDE.md、尤其要宣告某事「做不到」或放寬規則前，一定先實際查證（例如 ToolSearch 確認有沒有相關工具）；寫錯的規則比沒有規則更糟。**

## 規則九：隨時可接手＋用量到門檻自動收尾（2026-10-06 訂、2026-10-10 改版）

**收尾流程（觸發後依序做）**
1. 先回覆使用者：已完成哪些、還有哪些沒做（**照執行順序排**）。
2. 執行中的 agent：照上一條判斷——做得完的讓它做完；做不完的通知 30 分鐘內收尾：做完當前小步、commit＋push、未完成改動存 patch（寫路徑）、交最終報告。不再派新 agent。
3. 更新 交接紀錄「接手狀態」：下次從哪開始、全部待辦逐條照順序列（含驗收標準、排定的檢查日期、使用者已做的決定）。
4. 整理 交接紀錄檔，判斷工作日誌是否該搬到 封存檔（搬時同步補雷區索引）。
5. commit＋push，回報「已告一段落」。
- **7 天達收尾門檻的詳細版**（現行值讀設定檔 `dispatch-config.json` 的 `usageThresholdPct`，不寫死數字；2026-10-18 稽核更正：原寫死「97%」）（下次可能隔好幾天才接手，避免遺失脈絡）：除上述外，「接手狀態」每個待辦都要寫到「不看對話也能做」：背景與使用者原話、已查證的根因與證據、相關檔案／函式／commit、做到哪一步、下一步具體指令、驗收標準；另列「進行中的觀察」（例如回補進度、待驗證的上線項目）與其檢查方法；確認工作樹乾淨或 patch 已存。

**未達門檻時也要先評估用量夠不夠（2026-10-11 使用者要求）**：
- 開始任何新任務前（我自己接著做下一批、或使用者交代某項工作），先讀用量（`python ~/.claude/claude-dev-system/hooks/usage_guard.py --print`），估這個任務約要花多少 5 小時 % 與 7 天 %，對照「離收尾門檻（`dispatch-config.json` 的 `usageThresholdPct`，預設 80%／97%）還剩多少」與重置時間。
- **夠**：照排隊清單自動接下一批（或照使用者要求開工），開工時一句話說明預估用量。**不夠或很勉強**：開工前先告訴使用者——預估需要多少、目前剩多少、重置時間；提出選項（只做能完成的部分、先做最重要的細項、或等重置後再做），由使用者決定；不可做到一半才因額度中斷。多個 agent 平行時把預估相加；平行越多越容易一起撞上限。
- **收尾後若使用者再交代工作**：先依目前用量（usage.json／`--print`）與重置時間分析剩餘額度夠不夠做完、或能做完哪些部分（以近期同類工作的消耗估算），列給使用者決定，**不要直接開工**。

**平時就隨時保持可接手**（任何時候都可能被中斷）：
1. 每次派出／完成／中斷 agent、使用者新增或取消需求、發現新問題時，當下就更新「接手狀態」並 commit＋push。
2. 「接手狀態」完整列出：進行中的 agent（任務、進度、未提交 patch／worktree 位置、下一步、驗收標準）、排隊中的任務與順序、等待中的外部條件、排定的觀察／檢查（含日期時間）、使用者提過但未開工的全部待辦（逐條列，不可只寫「見某處」）、使用者已做的決定；每次對照最近對話與「目前已知問題」逐條核對沒漏項。
3. 派工都要求 agent 小步 commit＋push、未完成改動存 patch 到 scratchpad 並在回報寫路徑。多個 agent 平行很快吃完額度（10/6 四個約 1.5 小時撞 5 小時上限；10/8 兩個撞週上限），派工數量要節制。
- 接手時：先讀「接手狀態」，逐項確認 agent 是否還在跑（被中斷的用 SendMessage 接續或照記錄重派），再讀「常見雷區索引」「目前已知問題」。

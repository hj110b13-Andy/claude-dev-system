# 分階段模組化重整（claude-dev-system；使用者同意後才跑）

**最高原則**：功能完整與行為一致高於精簡、檔案數、架構美觀與省 token。刪除／合併／取代任何內容前，七項逐一確認並寫進紀錄：是否被其他檔呼叫、是否被動態載入／事件／設定檔／命令列使用、是否影響對外 API 或資料格式、是否負責錯誤處理／安全／相容性、是否在測試／建置／部署／排程裡、是否被 CLAUDE.md／hook／skill 依賴、是否有靜態看不出的隱含用途。任一不確定 → 列待確認，不刪。

**A 基準**：`git status` 確認沒有使用者未提交的工作（有就先問怎麼處理，不碰）；開獨立分支；跑現有測試並記錄已存在的失敗；`project-scan.py` 記下循環數、最大檔、依賴邊；盤點公開介面。測試跑不起來先修環境或建替代驗證，不能沒有基準就動手。

**B 保護**：對要動的模組補「固定輸入→固定輸出」的比對（`cds-safe-refactor` 第 2 步）；有畫面的專案先有 `cds-verify-app` 地圖；高風險區（資料層、權限、外部 API）標出來最後做。

**C 逐模組**（一次一個，每個獨立 commit）：確認原始行為 → 定義責任與介面（輸入、輸出、可呼叫誰、不可依賴誰、錯誤怎麼處理）→ 重構 → `depgraph.py` 確認循環數沒升、分層沒違規 → 單元測試 → `cds-blast-radius` 實跑一處 → 文件與設定 → 紀錄。不為了模組化而加沒有實際價值的抽象層；小功能不包成大架構。

**D 整合**：所有模組一起跑：介面呼叫、資料傳遞、狀態、錯誤傳遞、初始化與釋放、設定載入、外部服務、建置啟動、舊功能相容。各模組測試過不等於整體過。

**E 驗收**：重跑完整測試對照 A 的基準；有意改變的行為獨立列出；回歸問題修不了就保留證據、採可回復方式。不得為了宣稱完成而隱藏失敗或把未完成標完成。閘門（循環數、分層、`--check`）裝進測試或 CI。

**分段與用量**：每完成一個階段就更新 PROGRESS.md（做了什麼、剩什麼、下一步、驗證方式）並 commit；用量守門觸發就在階段邊界停。一場對話通常只做到 C 的一兩個模組，這是正常的，不要硬撐。

**回報格式**：執行摘要、原始問題與根因、重構後的目錄與介面、實際改動清單（新增／修改／合併／移動／刪除與原因）、測試結果（舊有失敗與新引入失敗分開）、仍未解決的風險、回復指引。
